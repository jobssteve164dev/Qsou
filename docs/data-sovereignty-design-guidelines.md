# Qsou 自主数据资产设计指导

> 状态：项目方向与数据设计的权威指导文件
>
> 生效日期：2026-08-04
>
> 适用范围：数据源接入、采集、存储、处理、索引、检索、监控、分析、导出与用户界面
>
> 说明：本文定义目标与验收边界，不代表所有能力已经实现。当前实现以代码和验证结果为准。

## 1. 项目要解决的问题

Qsou 的核心目标不是复制一个传统搜索引擎，而是建立一套自主掌握的投资数据资产：系统直接连接稳定数据源，持续保存可追溯、可验证、可回放的历史证据，并在这份自有数据之上提供搜索、监控和分析能力。

一句话定义：

> Qsou 是面向个人研究与决策的自主投资数据底座；搜索是使用数据的入口，不是数据来源本身。

项目的长期壁垒来自持续积累的数据历史、来源关系、版本变化、实体映射和用户反馈，而不是某个搜索界面、模型或外部服务。

## 2. 成功标准与非目标

### 2.1 成功标准

当以下能力同时成立，才能称为“自主掌握数据”：

1. 正式数据链不依赖传统搜索引擎才能持续运行。
2. 每条正式数据都能回答来自哪里、何时发现、何时抓取、保存了哪个版本。
3. 原始证据独立于解析器、Elasticsearch、Qdrant 和模型长期保存。
4. 任一派生存储损坏后，可以从已保存数据重建。
5. 每个正式数据源都有明确覆盖范围、采集频率、合法使用边界和健康状态。
6. 失败、缺口和延迟对系统可见，不以静默丢弃换取表面成功。
7. 用户可以用开放格式导出自己的数据，不被 Qsou 自身锁定。

### 2.2 非目标

- 不以覆盖整个互联网为目标；优先完整覆盖一组高价值、可持续的数据源。
- 不承诺替代交易所、监管机构或发行人的法定原始记录。
- 不把模型生成内容当作事实，不提供无证据的投资结论。
- 不把实时性、吞吐量或搜索相关性写成未经验证的对外承诺。
- 不因为“可以抓取”就默认拥有保存、再处理或再分发的权利。
- 不禁止传统搜索引擎；它可以用于发现潜在线索，但不能成为正式采集链的硬依赖。

### 2.3 市场定位与竞争边界

Qsou 不应在“网页数量最多”或“通用问答最全”上与传统搜索引擎竞争，也不应在项目早期复制大型金融终端的全部标准化数据。不同方案解决的问题并不相同：

| 方案类别 | 核心优势 | 对自主数据目标的结构性不足 |
|---|---|---|
| 传统搜索引擎 | 广泛发现、即时检索、使用门槛低 | 排名、覆盖与历史由平台控制，结果难形成可回放的自有资产 |
| 金融数据终端与供应商 | 标准化程度高、品类成熟、服务稳定 | 访问、许可、导出和价格由供应商决定，用户难掌握完整原始证据 |
| 通用采集与数据管道工具 | 连接器和调度能力强 | 通常不替用户定义金融来源覆盖、时间真实性和研究反馈闭环 |
| 本地知识库与 AI 搜索 | 私有语料可控、问答体验直接 | 多数从用户上传开始，不能保证外部来源持续采集和历史完整性 |

Qsou 的差异化位置是：在有限但高价值的来源集合上，把“直接采集、原始历史、证据追溯、版本变化、个人反馈”连成一个长期复利的数据资产。竞争壁垒的形成顺序应是：采集连续性 → 历史与版本深度 → 实体/事件关系 → 用户反馈与研究工作流；界面和模型负责放大资产价值，但本身不是壁垒。

初期服务对象是希望掌握个人研究数据的使用者。若未来对外提供数据产品，来源授权、再分发权、服务等级、客户数据隔离和删除责任必须作为新的商业边界单独确认，不能沿用“个人内部使用”的默认条件。

## 3. 不可妥协的设计原则

### 3.1 原始证据先于派生结果

解析、去重、分类、向量化和模型推理都会变化。系统必须先持久化原始响应及采集上下文，再确认采集任务完成。没有原始证据的结构化结果只能视为临时数据。

### 3.2 时间真实性先于“看起来完整”

发布日期、首次发现时间、抓取时间和进入搜索的时间不能混为一个字段。历史回测或时点查询必须只使用当时已经被系统看到的数据，禁止引入未来信息。

### 3.3 覆盖范围必须诚实

系统只能对已注册的数据源和已定义的时间窗口声明覆盖。不能用“抓到了一些结果”代替“完整覆盖了约定范围”。

### 3.4 来源优先级高于内容热度

优先连接交易所、监管机构、公司投资者关系页面和政府公开数据等一手来源。媒体、聚合站和搜索结果可以补充发现，但不能覆盖或抹去原始来源关系。

### 3.5 失败必须可见且可恢复

解析失败、发送失败、字段缺失、来源停更和数量异常都必须进入可观测状态。重试必须幂等，失败数据必须可回放，批次不能因局部错误整体静默丢失。

### 3.6 派生能力必须可替换

Elasticsearch、Qdrant、嵌入模型和大语言模型都是可替换的派生组件。替换它们不应破坏已采集的原始证据，也不应要求重新访问所有外部来源。

### 3.7 用户拥有可迁移的数据

关键数据与元数据必须支持 JSONL、CSV 或 Parquet 等开放格式导出。导出应包含来源、时间、版本和引用关系，而不只是搜索结果文本。

## 4. 数据权威分层

| 层级 | 内容 | 权威性 | 是否可重建 |
|---|---|---|---|
| L0 来源登记 | 来源身份、入口、覆盖契约、权利状态、采集策略 | 配置权威 | 需备份，不应从索引反推 |
| L1 原始证据 | HTTP 响应、文件、响应头、状态码、抓取上下文、内容哈希 | 事实权威 | 不可从下游完整重建 |
| L2 标准文档 | 规范化字段、正文、文档身份、版本关系、来源引用 | 结构化权威 | 可从 L1 按解析器版本重建 |
| L3 实体与事件 | 公司、证券、人物、公告、事件及其时间关系 | 领域派生层 | 可从 L1/L2 重算，但人工确认需单独保留 |
| L4 检索与向量索引 | Elasticsearch 索引、Qdrant 向量、聚合缓存 | 服务派生层 | 必须可重建 |
| L5 用户知识 | 收藏、标签、订阅、纠错、相关性反馈、研究笔记 | 用户资产 | 需独立备份和导出 |

权威关系必须单向清晰：L1 原始证据不能由 Elasticsearch 或 Qdrant 反向定义；删除索引不等于删除原始证据；需要合规删除时，应通过受审计的生命周期策略同步处理各层。

## 5. 目标数据流

```text
来源登记表
    ↓
采集调度与连接器
    ↓
L1 原始证据不可变归档 ──→ 完整性检查 / 缺口告警 / 重放队列
    ↓
规范化与版本识别
    ↓
实体关联与事件抽取
    ↓
Elasticsearch / Qdrant 等可重建索引
    ↓
搜索 / 订阅 / 证据查看 / 分析 / 导出
```

关键顺序是“先归档，后处理”。采集任务只有在原始证据完成持久化并得到稳定标识后，才能确认成功。解析、索引或模型处理失败不应触发重新访问来源；应优先从原始归档回放。

## 6. 来源治理契约

每个进入正式采集范围的数据源都必须登记，至少包含：

| 字段 | 要回答的问题 |
|---|---|
| `source_id` | 系统如何稳定识别该来源？ |
| `source_name` / `publisher` | 谁发布了信息？ |
| `authority_tier` | 一手来源、二手来源还是发现渠道？ |
| `entrypoints` | 从哪些 API、列表页、Feed 或文件入口采集？ |
| `document_types` | 该来源承诺覆盖哪些文档类型？ |
| `coverage_start` | 计划从哪个时间点开始保存历史？ |
| `collection_method` | API、Feed、静态页面、浏览器渲染还是人工导入？ |
| `schedule` | 期望采集频率和允许延迟是多少？ |
| `cursor_strategy` | 如何增量采集并防止漏页、跳页？ |
| `rights_status` | 访问、保存、处理、展示和导出的允许边界是什么？ |
| `retention_policy` | 原文、摘要和元数据分别保存多久？ |
| `owner` | 谁对接入质量和条款复核负责？ |
| `last_success_at` | 最近一次完整成功是什么时候？ |
| `latest_source_time` | 来源当前最新内容的时间是什么？ |
| `parser_version` | 当前由哪个解析器版本处理？ |
| `health_state` | 正常、延迟、缺口、阻断还是停用？ |

来源分为三类：

- 一手来源：正式数据的首选证据，如监管、交易所、公司公告与政府公开数据。
- 二手来源：用于补充语境、报道和发现，但必须保留其自身出处，不能伪装成一手证据。
- 发现渠道：搜索引擎、聚合页和外部推荐仅提供候选线索；正式入库前仍需回到可登记、可持续的来源入口。

来源接入顺序不按“网页看起来多”决定，应综合评估一手性、对研究决策的价值、历史可回补深度、更新稳定性、合法使用边界、采集与维护成本。优先选择少量可以长期完整覆盖的来源，再逐步扩展；不能用大量不稳定二手站点制造虚假的数据规模。

## 7. 文档身份、版本与去重

URL 不是稳定身份。一个 URL 可能更新内容，同一文档也可能出现在多个 URL。建议至少区分：

- `source_document_id`：来源自身提供的文档标识；没有时由稳定规则生成。
- `canonical_document_id`：Qsou 对同一逻辑文档的统一标识。
- `content_version_id`：某次内容版本的唯一标识，通常由规范化内容哈希与来源信息生成。
- `raw_object_id`：对应 L1 原始证据对象的稳定标识。

去重不能删除证据链。判断为重复时，应建立“此版本与哪个文档等价”的关系，并保留来源、抓取时间和原始对象。文档更新必须新增版本，而不是无记录地覆盖旧内容。

## 8. 时间模型

每条文档至少应区分以下时间：

| 字段 | 含义 |
|---|---|
| `source_published_at` | 来源声明的发布时间，可能缺失或被修改 |
| `first_seen_at` | Qsou 首次观察到该逻辑文档的时间 |
| `fetched_at` | 当前原始版本实际抓取完成的时间 |
| `processed_at` | 当前解析或处理版本完成的时间 |
| `indexed_at` | 当前版本进入可查询索引的时间 |
| `valid_from` | 该内容版本在来源侧开始有效的时间（能确定时） |
| `superseded_at` | 该版本被后续版本替代的时间 |

所有时间必须保存时区或统一为 UTC，并保留来源原始时间文本用于审计。任何“截至某时点”的查询都必须明确使用哪个时间语义；用于回测时，默认以 `first_seen_at` 或可证明的可用时间为边界。

## 9. 采集可靠性与完整性

### 9.1 最低可靠性要求

- 原始证据写入使用确定性标识和幂等操作。
- 任务确认发生在持久化之后，不发生在解析或发送之前。
- 每个处理阶段记录输入标识、输出标识、代码版本和错误原因。
- 失败数据进入可重放队列或死信集合，不静默跳过。
- 批处理允许逐项确认，局部失败不能抹掉已成功项或未处理项。
- 回补任务与实时任务使用相同的身份和版本规则。

### 9.2 完整性不是单一条数

每个来源都应建立可验证的覆盖契约，例如：

- 已知分页是否全部遍历。
- 来源声明总数与实际保存数是否相符。
- 连续时间窗口是否存在空洞。
- 文档编号、公告序号或游标是否跳号。
- 抓取量是否突然偏离历史区间。
- 来源最新时间与本地最新时间的差距是否超过承诺。
- 解析成功率和关键字段完整率是否突变。

系统界面必须把“来源没有新内容”“采集延迟”“采集失败”和“解析失败”显示为不同状态。

## 10. 存储、回放与灾难恢复

### 10.1 原始归档

原始证据应使用适合长期保存的对象存储或文件归档，保存响应正文、必要响应头、状态码、最终 URL、请求时间、采集器版本和内容哈希。格式可以是 WARC、原始文件加 JSON 元数据，或其他能够无损恢复证据的开放形式。

### 10.2 派生存储

- Elasticsearch：全文检索和聚合索引，不承担唯一事实源职责。
- Qdrant：语义检索派生索引，不承担正文或版本权威职责。
- 关系数据库：适合来源登记、任务状态、身份映射和用户资产，但具体选型不能改变分层原则。
- 缓存和队列：只负责加速与传递，不得成为唯一数据副本。

### 10.3 回放能力

系统应支持按来源、时间窗口、解析器版本或文档集合重放，且无需重新访问外部站点。每次重放必须保留处理版本，能够比较新旧输出，而不是覆盖后无法追责。

### 10.4 灾难恢复验收

“有备份”不等于“可恢复”。必须定期验证：

1. 从备份恢复来源登记与原始对象。
2. 从原始对象重建标准文档。
3. 从标准文档重建全文与向量索引。
4. 恢复用户标签、订阅和纠错记录。
5. 对比恢复前后的数量、哈希和关键查询结果。

## 11. AI 与自动分析边界

- 模型输出必须明确标识为推断，并引用支持它的原始或标准文档。
- 保存模型、提示词、处理代码和输入版本，保证结果可复算和可比较。
- 不确定时输出“不确定”或待核验状态，不用随机内容或无证据模板填补失败。
- 实体识别、事件抽取和相关性反馈应允许人工纠错；纠错属于用户资产，不应在重建索引时丢失。
- 模型升级不能改变原始证据，只能产生新的派生版本。
- 搜索摘要、事件标签和情绪判断不能被描述为投资建议或确定事实。

## 12. 合规、安全与数据生命周期

“自主掌握”指拥有持续获取、保存和使用数据的能力，不等于取得数据版权或无限再分发权。每个来源必须分别记录：

- 是否允许自动访问。
- 是否允许保存原文、附件、摘要和元数据。
- 是否允许模型处理、内部展示和对外导出。
- 是否包含个人信息、登录态数据或付费内容。
- 条款变更后如何暂停、删除、脱敏或仅保留元数据。

密钥、Cookie 和访问凭据不得进入原始内容或日志；公共数据、用户私有数据和系统运行数据必须有清晰隔离。删除请求应生成可审计的墓碑记录，并明确各层删除或保留依据。

具体合规判断以数据源所在司法辖区、服务条款和专业法律意见为准；项目文档不能替代法律结论。

## 13. 面向用户的产品动作

界面应围绕用户要完成的动作，而不是内部组件：

1. 查看我正在持续掌握哪些来源，以及哪里出现延迟或缺口。
2. 搜索自有资料库，并直接打开来源证据和历史版本。
3. 订阅公司、主题或事件，在新增与变更发生时收到提醒。
4. 比较同一文档或事实在不同时间的变化。
5. 标记相关性、纠正实体关系、保存研究笔记。
6. 导出选定数据及完整来源、时间和版本元数据。

用户不应被要求理解消息队列、索引别名、向量维度或解析器内部差异。只有当某个差异会改变用户的选择、成本、风险或结果时，才应在治理界面暴露。

## 14. 验收指标

优先验收数据资产是否成立，再验收搜索体验。建议按以下口径衡量：

| 维度 | 核心指标 |
|---|---|
| 证据完整性 | 正式文档关联原始对象的比例，目标应为 100% |
| 来源覆盖 | 已履行覆盖契约的来源比例；按来源分别展示，不合并掩盖 |
| 新鲜度 | `first_seen_at - source_published_at` 的分位数及超期比例 |
| 管道可靠性 | 各阶段成功率、死信数量、重放成功率、未解释缺口数 |
| 数据质量 | 关键字段完整率、重复率、解析漂移率、实体映射准确率 |
| 可恢复性 | 最近一次全链路恢复演练是否成功、耗时和差异数量 |
| 可迁移性 | 导出能否脱离 Qsou 被独立读取，并保留来源与版本关系 |
| 用户价值 | 告警采纳率、搜索后打开证据率、人工纠错后质量提升 |

性能目标必须在明确数据量、硬件和查询模型下通过测试后确定，不在设计文档中预设未经验证的数字。

## 15. 实施优先级

不修改现有路线图状态的前提下，后续设计和实现应遵循以下依赖顺序：

1. **数据地基**：来源登记、稳定身份、时间模型、L1 原始证据归档。
2. **连续性**：幂等采集、缺口检测、死信、回补、版本保留和回放。
3. **可用性**：从标准文档重建 Elasticsearch/Qdrant，提供证据可追溯的搜索与订阅。
4. **资产增值**：实体图谱、事件抽取、用户反馈、研究工作流和可替换的 AI 分析。

如果某项上层功能要求牺牲原始证据、时间真实性或可回放性，应调整上层方案，而不是削弱数据地基。

## 16. 设计评审清单

任何新增数据源、处理器、模型、索引或用户功能在合并前应回答：

- 它是否强化了直接数据来源，而不是制造新的外部搜索依赖？
- 原始证据在何处持久化，稳定标识是什么？
- 来源、时间、版本和处理代码能否完整追溯？
- 失败是否可见、可重试、可回放且不会重复写坏数据？
- Elasticsearch、Qdrant 或模型被替换后能否重建？
- 覆盖范围和缺口如何被证明，而不是凭感觉判断？
- 权利、隐私、保留与导出边界是否已经登记？
- 用户是否只需理解自己的目标和选择，而不必承担内部复杂度？
- 是否新增了无法导出的用户资产或无法解释的模型结论？
- 验收依据是实际数据和恢复演练，还是未经验证的文档承诺？

任何一项没有答案，都应记录为设计缺口，不能用“后续优化”掩盖其对数据资产成立性的影响。
